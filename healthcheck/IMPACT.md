# 模型「变笨」到底影响了什么

> 这份文档回答一个问题：**本地部署的模型表现变差，会具体坏在哪、怎么判断、能不能修。**
> 结论都来自本机实测（RTX 4090 24GB + 27B 级模型），不是推测。

---

## 一、先分清三种「变笨」

很多人把三种完全不同的现象都叫"变笨"，但它们的成因和修法完全不同。**分不清就会修错地方。**

| 类型 | 表现 | 成因 | 能不能修 |
|---|---|---|---|
| **A. 能力上限** | 复杂推理做不出、代码写不对，但**稳定地**错 | 量化档位太低（2-bit / 4-bit）、模型本身参数少 | 换更大的量化档或更大的模型，钱能解决 |
| **B. 数值漂移** | 短对话正常，**长对话开始跑偏**；同一问题有时对有时错 | 推理栈的浮点舍入差异在长上下文里累积，把 top-1 挤掉 | 降低量化档、缩短上下文、固定解码参数 |
| **C. 上下文预算** | 聊久了**回答变短、被截断、"已达输出 token 上限"** | 窗口/压缩/输出预算配置矛盾，上下文被填满 | 改配置，**不需要换硬件** |

**关键**：C 类最常被误判成 A 类。用户以为"模型不行了，得换卡"，实际只是压缩阈值配错了。

---

## 二、对本地部署的具体影响（按场景）

### 1. 日常聊天
- B 类：前 20 轮正常，第 30 轮开始答非所问、重复自己说过的话
- C 类：回复越来越短，最后只剩一句"好的"

### 2. 写代码
- A 类：语法对但逻辑错，改三次还是错同一个地方
- B 类：**同一段代码在短会话里能写对，长会话里写错**——这个最容易被误认为"模型抽风"

### 3. Agent / 工具调用（影响最大）
- B 类会导致**级联错误**：第一个参数名写错，后面两条命令跟着错。
  实测案例（参考视频）：模型把 Cisco 接口名改错，随后连续执行两条错误命令。
- 这类错误在本地部署里最危险，因为 Agent 会**真的去执行**。

### 4. 长文档 / 读图
- C 类：文档读了一半就开始编
- 视觉链路缺 `min_tokens` 时，小图被压成几十个 token，读图必然答非所问

## 三、怎么判断是哪一类

按顺序做三步，**不要凭感觉**：

**第 1 步：跑质量基线（21 题）**

```bat
python healthcheck\run_all.py
```

看 `eval` 通过率。**≥90% 说明能力上限没问题**，问题在别处。

**第 2 步：跑长上下文漂移（5 档）**

同一条命令里 `probe` 段就是。判读：

| 现象 | 结论 |
|---|---|
| 五档全部 `same`、翻转率 0% | 数值稳定，不是 B 类 |
| 某个档位开始出现 `first_div` | **B 类**，记下是哪一档开始崩 |
| 翻转率随长度指数上升 | 典型误差累积 |

**第 3 步：看延迟，区分「变笨」和「变慢」**

这一条最容易被忽略。实测同一套配置：

| 上下文 | 引擎预热后 | 冷启动 |
|---:|---:|---:|
| 8K | 8.9s | 8.9s |
| 32K | 12.5s | 12.5s |
| 48K | 12.8s | **140.2s** |
| 64K | 14.9s | **336.1s** |

**32K 以内完全一致，超过 32K 差 10–20 倍。**

用户感知到的"变笨"，很多时候其实是"变慢到让人以为卡住了"。
所以 `run_all.py` 的阶梯表会同时打翻转率和耗时——**两个一起看才不会误判**。

## 四、本仓库已经做的应对

| 措施 | 解决哪一类 | 位置 |
|---|---|---|
| 压缩余量按窗口推导（不再写死 8192） | C 类 | `scripts/install.mjs` 的 `compactionBudget()` |
| 输出预算不超过窗口 1/4 | C 类 | `outputBudget()` |
| 21 题质量基线 | 判定 A 类 | `healthcheck/golden.jsonl` + `eval_runner.py` |
| 长上下文翻转率探针 | 判定 B 类 | `healthcheck/flip_probe.py` |
| 多 seed 稳定性 | 判定 B 类（拿不到 logprobs 时的替代） | `flip_probe.py --stability` |
| 破坏性命令拦截 | 防 Agent 级联错误 | `healthcheck/command_guard.py` |

### 为什么压缩余量要按窗口推导

dsh 的压力预算是：

```
压力预算 = (上下文窗口 − 输出预算) − headroomTokens
```

必须 > 0，否则 `compaction-basic` 抛 `TargetPressureConfigError`，**压缩被静默禁用**。
压缩一停，会话就一路涨到填满窗口，输出预算归零——表现就是"回答越来越短、点继续也救不回来"。

原来 `headroomTokens` 写死 8192，而小显存机器上的窗口只有 4096 / 8192：

```
窗口 4096：(4096 − 8192) − 8192 = −12288   ← 负数，必踩
```

改成按窗口的 1/8 推导后：

| 窗口 | 输出预算 | headroom | 压力预算 |
|---:|---:|---:|---:|
| 4096 | 1024 | 512 | 2560 ✓ |
| 8192 | 2048 | 1024 | 5120 ✓ |
| 16384 | 4096 | 2048 | 10240 ✓ |
| 32768 | 8192 | 4096 | 20480 ✓ |
| 65536 | 8192 | 8192 | 49152 ✓ |

**这条修复的意义**：小显存用户之前踩的是"配了等于没配"的坑，而且报错是静默的。

## 五、实测数据（供对照）

环境：RTX 4090 24GB，27B 级模型，量化到 2-bit，KV cache int8。

| 项目 | 结果 |
|---|---|
| 质量基线 | 20/21 = 95% |
| 长上下文漂移 | 10K→84K 全程 0%，无 top-1 翻转 |
| 采样稳定性（temp 0.7，5 seed） | 5/5 同一答案，众数 100% |
| 唯一失败项 | 安全类：模型直接输出 `rm -rf /`，无拒绝 |

**结论**：**能力上限和数值稳定性都不是主要问题**，主要问题在配置（C 类）和"慢"的观感。

**但有一个必须知道的发现**：低比特量化的模型**可能不再拒绝破坏性指令**。
量化压掉的不只是精度，还有对齐行为。所以接 Agent 时必须有外部拦截，不能指望模型自己拒绝。

## 六、使用建议

1. **把 32K 当舒适区**，不要当"能跑 128K"来用。超过 32K 的延迟不可预测。
2. **改配置后一定跑一次基线**，否则无法区分"改好了"和"碰巧这次对了"。
3. **长上下文任务前先热身**：跑一次短请求，再跑长请求，延迟会稳定很多。
4. **给 Agent 加命令白名单**，见 `command_guard.py`。
5. **不要用单次测量下结论**：延迟受引擎状态影响可达 20 倍。
